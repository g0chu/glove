# AGENTS.md

Discord bot bridging guild text channels to any OpenAI-compatible Chat Completions endpoint. TypeScript (ESM, NodeNext, strict), discord.js v14 + native `fetch`; runtime deps are only `discord.js`/`dotenv`. Node >= 22.15 (built-in zstd is needed by the ZIM reader). No linter, formatter, or CI.

## 1. Project Overview & Architecture

@mention the bot in a text channel of the configured guild (`DISCORD_GUILD_ID`; empty = any guild the bot is a member of) and it forwards the channel's recent conversation to the model, streaming the answer back as a live-updating message. Every *trackable* message (a human's or another bot's message in a text channel of the target guild; the bot's own messages are never tracked, other bots are labeled `(bot)` in the context) is committed to the channel's conversation store once it has been stable (unchanged) for `DISCORD_MESSAGE_STABLE_MS`; *mentions* — from humans or other bots alike — queue a turn, and with `BOT_CHIME_ENABLED` a non-mention message from another bot queues a turn the model may decline (chime).

- **Stability gate** (`bot/gate.ts`) — a trackable message is committed (tracked in the context, able to queue a turn) only once it has been unchanged for `DISCORD_MESSAGE_STABLE_MS` (default 2000, 0 = commit on arrival). Every edit while pending restarts the window and updates the stored state, so the commit carries the message's *final* content — this is what makes other bots' streamed replies (posted as a placeholder, edited as the text arrives) reach the model complete, and what keeps a mention that only exists in the final form from queueing one turn per partial edit. A message deleted (or whose channel is deleted) while still pending never commits; commits are evaluated on final content, so `!clear` and mentions are decided from the completed message. Edits after the commit sync the context through the usual update path.
- **Context** (`llm/context.ts`) — per-channel in-memory context, seeded once with the channel's last `MODEL_CONTEXT_MAX_MESSAGES` messages (live fetch, survives restarts; Discord's fetch caps at 100, so a bigger N seeds with what Discord can give), then only grows. When the context size passes `CONTEXT_COMPACTION_MAX_TOKENS`, everything older than the newest `CONTEXT_COMPACTION_KEEP_MESSAGES` messages is folded into a model-written summary (one tool-less chat call to the same endpoint, sent as a *user* message, ≤4000 chars). The size is the endpoint's own measured prompt size when known (see Metrics), else the token estimate (~4 chars/token). The turn's mention is never folded or trimmed. The budget can be left empty in `.env` to be set automatically (window − completion headroom, see Metrics), and a request that overfills the window anyway is caught and recovered (overflow recovery below).
- **Chime** — `BOT_CHIME_ENABLED` (default `false`): a message from *another bot* that does not mention the bot queues a *chime turn* — the model first makes one small tool-less YES/NO decision over the channel transcript (`bot/chime.ts`; the transcript ends with the triggering message, the reply's system prompt is not part of it). YES runs a normal turn (streamed reply, tools and all); NO, a garbage/empty answer, or a failed call stays completely silent (no typing indicator, no message, nothing recorded — a broken decision must not post an unasked-for reply). Mentions from any author always respond (no decision); human non-mentions are ambient context only.
- **Clear** — `!clear` in a text channel resets that channel's model context for a fresh chat: `reset()` drops entries + summary and suppresses the startup seed (no re-seed). The command is neither tracked nor answered (a bot mention alongside it is swallowed too); only humans may issue it (other bots' messages are tracked now, so a bot posting `!clear` is just context). The bot posts a confirmation line (🧹, a UI line, never context). Mentions queued before the clear are skipped (their message left the context).
- **Turn** — `runToolTurn` (`tools/loop.ts`): model ↔ tool rounds capped by `TOOLS_MAX_ROUNDS`; tool results live only in the turn. Then `ResponseWriter` posts the final reply. Only the final reply reaches channel history; the tool-activity message (one per turn — posted on the first call, edited in place for every later call, oldest lines collapsing into a "… N earlier calls …" header past 2000 chars), the thinking (🤔) lines, and the intermediate rounds' text (settled in place between the activity lines) are posted but never tracked.
- **Images** — `MODEL_ENABLE_IMAGES=true`: image attachments (png/jpeg/webp/gif) of the newest `MODEL_CONTEXT_MAX_MESSAGES` entries are downloaded per turn from the Discord CDN (≤4 per message, `MODEL_IMAGES_MAX_BYTES` cap) and sent as base64 `image_url` parts; unsent attachments leave a one-line note.
- **Files** — `MODEL_ENABLE_FILE_CONTENTS=true`: the text content of non-image attachments of the newest `MODEL_CONTEXT_MAX_MESSAGES` entries is downloaded per turn from the Discord CDN (≤3 per message, `MODEL_FILE_CONTENT_MAX_BYTES` cap) and inlined into the message's context text as a labeled, fenced block (the fence grows past any backtick run in the content). Only readable text (valid UTF-8, no NUL bytes) is inlined; binary files, oversized ones, and download failures leave a one-line note. The pipelines are mutually exclusive per attachment type: with file contents on, the image pipeline only references image attachments (no "unsupported type" notes for files); off, behavior is unchanged.
- **Tools** — four opt-in in-process families (default `false`): `WEBTOOLS_ENABLED` (DuckDuckGo search + SSRF-protected fetch), `FILETOOLS_ENABLED` (read/write/edit confined to `FILETOOLS_WORKSPACE`, default `./workspace`, which must exist), `SHELLTOOLS_ENABLED` (run a shell command via /bin/sh in the file workspace; per-command deadline + combined output cap), `ZIMTOOLS_ENABLED` (offline Wikipedia, `ZIM_FILE` → ZIM v6 archive). The system prompt note (`tools/index.ts`, built by `buildTools`) lists exactly the enabled families — the model is never told about disabled ones; the ZIM no-match hint only suggests `web_search` when the web family is enabled.
- **Metrics** (`llm/metrics.ts`) — the model side's own tokenizer counts. `LlmClient.chat` captures `ChatResult.usage` whenever the response reports token counts (OpenAI `usage` block; llama.cpp's legacy top-level `prompt_tokens`/`completion_tokens`; or the `timings` block the final streaming chunk carries — `prompt_n + cache_n` prompt tokens, `predicted_n` completion tokens; llama-server sends the first two non-stream and timings stream). Every model call of a turn (reply tool rounds, the compaction summarizer, the chime decision) runs through a `TurnTokens` wrapper: at the end of the turn the summed input/output tokens are logged, and the turn's largest prompt becomes the channel's *measured* context size — what the compaction trigger compares against `CONTEXT_COMPACTION_MAX_TOKENS` in preference to the char estimate (a compaction attempt forgets it; `!clear` does too). With `MODEL_METRICS_ENABLED` the llama-server's `GET /slots` (base `MODEL_METRICS_URL`, default the chat endpoint's origin; per-probe timeout `MODEL_METRICS_TIMEOUT_MS`) is additionally probed at startup and after every turn: the context window and current use are logged ("server context X/Y tokens"), the startup probe warns when the compaction budget is not below the window, and when the endpoint reports no usage the slot's last-request token count is the fallback measurement. With `CONTEXT_COMPACTION_MAX_TOKENS` left empty (present but blank; a missing variable keeps the default), the budget is set automatically from the first successful probe: window minus the completion headroom (4096 tokens, `COMPACT_OUTPUT_RESERVE_TOKENS`) — the 4000 fallback applies until then, and a too-small window gives up after one warning. All probes are best-effort — a broken endpoint resolves to null and never kills a turn.
- **Overflow recovery** (`index.ts`) — when a turn's request overfills the model's context, the endpoint rejects it before generating (llama.cpp: HTTP 400, `"request (N tokens) exceeds the available context size (M tokens)"` — JSON body in stream and non-stream alike). The bot recognizes the overflow error (`isContextOverflowError`, a few endpoint phrasings), reads the window from the error when it carries one, shrinks the channel context with `emergencyShrink` (oldest entries first, never the turn's mention; the running summary is dropped only when the entries alone still do not fit; target = the smaller of the compaction budget and window − headroom), rebuilds the turn's context, and retries the model once — a second overflow (e.g. the mention alone is too big) falls through to the ordinary error path. The pre-overflow measurement is forgotten (it described the overfilled context).

## 2. Build & Development Commands

```bash
npm install               # npm only (package-lock.json present)
cp .env.example .env      # fill in values; .env is gitignored
npm run dev               # run from source (tsx)
npm run build && npm start  # compile src/ -> dist/ and run
npm run typecheck         # tsc --noEmit
npm test                  # smoke tests (tsx test/smoke.ts)
```

- **Done means green**: `npm test` **and** `npm run typecheck` — `tsx` does not typecheck, so a green test run proves nothing about types.
- Required env: `DISCORD_TOKEN`, `MODEL_API_URL`; `DISCORD_GUILD_ID` is optional (empty = respond in every text channel of every guild the bot is in); everything else in `.env.example`.

## 3. Testing Guidelines

- Whole suite is `test/smoke.ts` via `npm test` — no framework, no selection, no config. Hermetic: mock OpenAI-compatible HTTP server on an ephemeral port, fake Discord channels, injected DNS/search backends, temp workspace dirs; no `.env`/Discord/network needed.
- Plain `node:assert/strict`; `ok(name)` check groups (currently **126**); the final line prints the count.
- Async is driven with `ticks()` (`setImmediate`), not real sleeps.
- In tests use the pure `parseConfig(env)`, never `loadConfig()` (calls `process.exit(1)`).
- Web-tool tests use `WebToolsOptions.allowPrivate`/`resolver`/`searchFetch` — tests-only escape hatches, never enable in production.

## 4. Code Style & Naming Conventions

- Relative imports need explicit `.js` extensions even in `.ts` files: `import { x } from "./bot/queue.js"`.
- 2-space indent, double quotes, semicolons; `import type` for type-only imports; explicit return types on exported functions; JSDoc on exported symbols.
- Lowercase error messages without a trailing period; log via `src/log.ts`, never bare `console.log` outside `log.ts`/config errors.
- Defensive by default: malformed model input/SSE/Discord errors are tolerated where it keeps the bot alive; a broken tool becomes an `Error: …` tool result, never a crash.
- Naming: `PascalCase` types, `camelCase` functions/vars, `UPPER_SNAKE` constants/env, lowercase filenames.
- Do not add runtime dependencies without confirming with the user.

## 5. Working Agreements

- The user drives commits — don't commit unless explicitly asked (style: conventional subjects, `feat: …`/`fix: …`).
- Never edit or commit: `dist/`, `workspace/`, `.env`, `node_modules/`.
- Ask before: changing queue/history/writer/context semantics pinned by tests, changing the SSRF blocklist or workspace-confinement rules, or enabling tools in `.env`.
- No CI — `npm test` + `npm run typecheck` are the only gates; keep changes self-contained.

## Behavior pinned by `test/smoke.ts` (change only together with the tests)

- **Queue**: per-channel FIFO; one turn at a time per channel (channels run concurrently); holds *turn requests* `{id, chime}` in arrival order — mentions (`chime: false`, always respond) and, with `BOT_CHIME_ENABLED`, other bots' non-mention messages (`chime: true`); a trigger whose message left the context is skipped.
- **Chime**: `decideChime` is one tool-less chat call (system prompt + transcript, no tools on the wire) — YES only when the trimmed, uppercased answer starts with "YES"; NO, garbage, an empty answer, and a failed call all stay silent (logged, never a posted reply). A chime turn decides after the context is built (seed + compaction included) and before the writer starts, so a NO leaves no trace in the channel.
- **Stability gate**: a message commits exactly once, when it has been unchanged for `DISCORD_MESSAGE_STABLE_MS` (edits restart the window; the commit carries the latest state); a stale timer re-firing is a no-op (only the still-stored entry commits). A message dropped while pending (delete / channel delete / shutdown) never commits, even if its cancelled timer fires. `onCommit` (in `index.ts`) evaluates the *final* content: a human's `!clear` resets the context and is neither tracked nor answered; otherwise the message enters the context (labeled `(bot)` for bot authors) and a mention from any author queues exactly one turn — an edit that adds or removes the mention before stabilization decides. Edits after the commit sync the context in place (a chunked reply is one entry with one id per chunk; any chunk id resolves it; a chunk edit rebuilds the text; a chunk delete drops the whole reply); deletes remove the entry.
- **Clear**: `!clear` (trimmed, case-insensitive, bot mentions stripped, evaluated on the committed/final content) resets the channel context: `reset()` drops entries + summary and marks the seed as taken (no re-seed) — a pre-clear mention → null. The 🧹 confirmation line is a UI line, never context; the command itself is never tracked or answered. Only human authors may issue it (other bots' `!clear` is just a tracked message).
- **Compaction**: the seed merges the live last-N with what already arrived, chronologically by `createdTimestamp`, ties broken by snowflake id (`compareDiscordIds` — the API returns newest-first, so same-millisecond bursts must not keep that order; tracked ids win). The seed fetch is capped at Discord's 100-message limit (a bigger window seeds with what Discord can give). The trigger size is the channel's measured tokens (the endpoint's own count of the last turn's largest prompt) when known, else the char estimate — over budget → `compact()` folds everything older than the keep window (plus any existing summary) via one tool-less call — never the turn's mention — and the measurement is forgotten (it then describes the pre-compaction context); on summarizer failure or nothing foldable → `emergencyTrim` drops the oldest entries (never the mention) until the estimate fits. An empty (present-but-blank) `CONTEXT_COMPACTION_MAX_TOKENS` switches the budget to automatic: window minus `COMPACT_OUTPUT_RESERVE_TOKENS` headroom from the first successful /slots probe (4000 fallback until then; too-small window → give up after one warning; missing variable = the plain default). If a request overfills the window anyway, `isContextOverflowError` (llama.cpp's `exceed_context_size` rejection, a few other phrasings) → `emergencyShrink` (oldest first, mention never dropped, summary dropped last) to `min(budget, window − headroom)` → rebuild → **one retry**; a second overflow is the ordinary error path.
- **Turn context**: system prompt first, then the summary as a labeled user message, then entries in order — user entries prefixed `Name: …` (`Name (bot): …` for other bots), the bot's own replies as unlabeled assistant messages, textless entries with no images and no file blocks dropped. If the mention is no longer in the context (deleted), the turn is skipped. Every other message is its own user message, never merged; recorded replies appear once with canonical text; tool/thinking lines never appear.
- **LLM client**: the per-request timeout covers the whole stream; `abort()` cancels all in-flight requests. `tools`/`tool_choice` are sent only with a non-empty registry; streamed `delta.tool_calls` are reassembled by index. `chat()` takes `StreamCallbacks { onDelta?, onReasoning? }`; reasoning is never part of the result. `ChatResult.usage` is set whenever the response reports token counts — `usage` block, llama.cpp's legacy top-level counters, or the final chunk's `timings` (prompt_n + cache_n / predicted_n) — and left absent otherwise. Message `content` is a string or an array of text/image parts (pass through to the wire unchanged).
- **Writer**: ≤2000 chars; `splitForDiscord` never splits inside a code fence (closes it, reopens in the next chunk), keeps tables together (a spanning table repeats its header row), prefers paragraph/heading/list boundaries. While thinking, a live message shows the streamed reasoning (whole text while it fits; otherwise header + "*N lines hidden*" + last 5 lines), completing in place to a terminal line — the first line of the thinking (truncated after 50 chars, `...` when cut) plus how long it took, e.g. "🤔 *Let me check the units first. (12s)*" — when the reply starts, when a tool round ends (`discard()`), or at finish when nothing streamed; every round's reasoning thus persists as its own terminal line, not just the final one. The reply then streams in its own fresh live message(s) (only the growing last chunk is edited, throttled; a new live message is created per chunk; each settles in place at finish, remaining chunks posted fresh). Reasoning is never posted or recorded in full. `discard()` (used between tool rounds) settles the round's reply text in place (the live messages are completed to the round's full text, so the round's narration stays in the channel above the next tool-activity lines) and completes its thinking message into the terminal line instead of deleting it. `format.ts` rewrites `$…$` math to Unicode before posting/record (non-math `$` untouched).
- **Tool loop**: a round ending in tool calls persists its *text* (the streamed preview is settled in place via `onToolRound` → `writer.discard()`, so the round's narration stays in the channel above the tool-activity messages; `discard()` also completes the round's thinking into a terminal line so the reasoning shows between the tool-activity messages). `onToolRound` never fires for the cutoff round — its text is the final reply, posted (and recorded) by the caller's `finish()`. `onToolCalls` is **awaited** right before execution (the caller records the round's calls in one shared activity message per turn — `ToolActivityPoster`: the first round posts it, every later round edits it in place, so a turn with N calls across R rounds costs one new Discord message + R-1 edits; past 2000 chars the oldest lines are dropped behind a "… N earlier calls …" header that keeps a leading icon so the message stays a UI line; a failed post/edit is retried on the next round. Each line: icon + name + up to two args, results never shown); tools execute concurrently; results become `tool`-role messages that live only in the turn. `TOOLS_MAX_ROUNDS` caps the rounds; exhaustion with no text posts a note.
- **Tool security**: `web_fetch` validates URLs against an SSRF blocklist, connects to the pinned resolved IP (anti-DNS-rebinding), re-validates redirects hop by hop, and refuses mixed public/private resolution. File paths are confined to the workspace (symlink escapes, including dangling, rejected); reads refuse binaries, writes are capped. `shell_exec` is not sandboxed — commands run via /bin/sh in the file workspace with a per-command deadline and a combined output cap (a kill returns the partial output); in-flight commands are killed with the tool stack. ZIM reads are read-only and bounded: single fd with targeted reads (never mmap'd), size-capped LRU entry/cluster caches, time-budgeted title scans, hop-capped redirects with loop detection.

## Gotchas

- The bot needs the **MESSAGE CONTENT privileged intent** enabled (Developer Portal → app → Bot → Privileged Gateway Intents); without it, message content silently arrives empty.
- `MODEL_ENABLE_IMAGES=true` requires a vision-capable endpoint; images are downloaded at turn time only (last-N window), never on message arrival. File contents (`MODEL_ENABLE_FILE_CONTENTS`) are likewise inlined at turn time only; a non-text file (binary, NUL bytes, invalid UTF-8, empty) is never inlined — it leaves a note, like an oversized image.
- Keep `CONTEXT_COMPACTION_MAX_TOKENS` comfortably below the llama-server context size (`-c`, default only 4096), and `CONTEXT_COMPACTION_KEEP_MESSAGES` small enough that keep-messages + summary fit — otherwise `emergencyTrim` starts dropping recent messages. Without metrics the trigger is a char heuristic (~4 chars/token), not a real tokenizer; with `MODEL_METRICS_ENABLED` (or any endpoint that reports usage) it is the endpoint's measured prompt count instead — note it includes the chat-template overhead, so it runs slightly higher than the estimate for the same content. The automatic budget (empty `CONTEXT_COMPACTION_MAX_TOKENS`) derives window − 4096 — that keeps the window nearly full, so prompts (and prompt processing) get large; pin a smaller number when per-request latency matters. Overflow recovery (one shrink + retry) catches what slips past the budget, but it drops the oldest messages without a summary — the budget should still do its job. With metrics on, the startup probe warns when the budget is not below the server's context window.
- The endpoint must support function calling (llama.cpp needs a tool-capable chat template); if it rejects `tools`, keep the `*_ENABLED` flags off.
- `FILETOOLS_WORKSPACE` (default `./workspace`) must exist — not created automatically; failures surface per call and the turn continues. The shell tool runs in that same directory, so it needs the directory too.
- ZIM: v6 only (Wikipedia clusters are zstd-compressed → Node >= 22.15); LZMA2 clusters/non-v6 surface as per-call errors, never crashes. `wikipedia_search` matches titles/paths only (exact → prefix → budgeted substring scan), not article bodies; `wikipedia_read` returns clean text (references/TOC/nav dropped), truncated to `TOOLS_MAX_RESULT_CHARS`.
