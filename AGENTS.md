# AGENTS.md

Discord bot bridging guild text channels to any OpenAI-compatible Chat Completions endpoint. TypeScript (ESM, NodeNext, strict), discord.js v14 + native `fetch`; runtime deps are only `discord.js`/`dotenv`. Node >= 22.15 (built-in zstd is needed by the ZIM reader). No linter, formatter, or CI.

## 1. Project Overview & Architecture

@mention the bot in a text channel of the configured guild (`DISCORD_GUILD_ID`; empty = any guild the bot is a member of) and it forwards the channel's recent conversation to the model, streaming the answer back as a live-updating message. Every *trackable* message (a human's or another bot's message in a text channel of the target guild; the bot's own messages are never tracked, other bots are labeled `(bot)` in the context) is committed to the channel's conversation store once it has been stable (unchanged) for `DISCORD_MESSAGE_STABLE_MS`; *mentions* — from humans or other bots alike — queue a turn, and with `BOT_CHIME_ENABLED` any non-mention message (a human's or another bot's) queues a chime turn: the model waits for complete stillness in the channel, then decides whether to respond at all (a NO posts the decision + reason).

- **Stability gate** (`bot/gate.ts`) — a trackable message is committed (tracked in the context, able to queue a turn) only once it has been unchanged for `DISCORD_MESSAGE_STABLE_MS` (default 2000, 0 = commit on arrival). Every edit while pending restarts the window and updates the stored state, so the commit carries the message's *final* content — this is what makes other bots' streamed replies (posted as a placeholder, edited as the text arrives) reach the model complete, and what keeps a mention that only exists in the final form from queueing one turn per partial edit. A message deleted (or whose channel is deleted) while still pending never commits; commits are evaluated on final content, so `!clear` and mentions are decided from the completed message. Edits after the commit sync the context through the usual update path.
- **Prompt interruption** (`bot/quiet.ts`) — while a turn's attempt is running, any change in the channel it is answering (a new trackable message, an edit of one, or a typing indicator; the bot's own posts and typing never count) interrupts it: the attempt's in-flight model request is aborted through the caller's `AbortSignal` (`LlmClient.chat` reports it as an `InterruptedError`, never a timeout), the partial reply is withdrawn (`writer.interrupt()` — the live partial messages are deleted, the round's thinking line completes in place and is kept, like a finished round's), and the turn waits for the channel to go quiet — no activity for `DISCORD_MESSAGE_STABLE_MS`, the window restarting on every new change (`ChannelActivity.waitForQuiet`) — so that every message that arrived while the attempt was interrupted has committed (and queued its own turn, when it queues one) before the interrupted turn is judged: **superseded → discarded** (a chime turn by any newer committed user entry — the newer message's own turn decides over the still conversation; a mention turn by a newer pending mention turn — it always responds, over a context that carries everything, so it answers the newest information; a discarded turn is never completed later and records nothing) and **not superseded → retried** (the interruption carried no new message — an edit, a typing indicator — so nothing else will answer, and the turn retries as a fresh attempt with a freshly built context, which carries everything that arrived or changed while it waited). An interrupted attempt records nothing either way: the channel context (and the model's history) keep only the attempt that completes; a turn whose trigger left the context while it waited for quiet skips. `ChannelActivity` tracks per-channel last-change timestamps (`note`) and per-channel watchers (`watch`, fired on every note — the attempt uses one to abort its request); `clearChannel`/`clear` forget a channel's state (a deleted channel's turn must not keep waiting).
- **Context** (`llm/context.ts`, `llm/persist.ts`) — per-channel context holding the **whole conversation the model has seen**: every trackable message, every completed turn recorded in full (each tool round's text, reasoning, tool calls and results as their own entries, plus the final reply), persisted to `CHATS_FILE` (default `./data/chats.json`) after every change, so a restart resumes each conversation exactly where it left off instead of re-seeding (the file is the source of truth; a channel without a persisted entry gets the usual one-time seed of the channel's last `MODEL_CONTEXT_MAX_MESSAGES` messages, and a restored conversation gets one catch-up seed at its first turn to merge in what arrived while the bot was offline — already-tracked ids win, Discord's fetch caps at 100). The context then only grows. When the context size passes `CONTEXT_COMPACTION_MAX_TOKENS`, everything older than the newest `CONTEXT_COMPACTION_KEEP_MESSAGES` messages is folded into a model-written summary (one tool-less chat call to the same endpoint, sent as a *user* message, ≤4000 chars; a fold boundary never splits a tool-call group). The size is the endpoint's own measured prompt size when known (see Metrics), else the token estimate (~4 chars/token, counting reasoning and tool calls). The turn's mention is never folded or trimmed. The budget can be left empty in `.env` to be set automatically (window − completion headroom, see Metrics), and a request that overfills the window anyway is caught and recovered (overflow recovery below).
- **Chime** — `BOT_CHIME_ENABLED` (default `false`): any trackable message that does not mention the bot (a human's or another bot's) queues a *chime turn*. A chime turn decides over a **still conversation**: before deciding it waits for complete stillness in the channel (no activity for `DISCORD_MESSAGE_STABLE_MS`, the window restarting on every new change — a new message, an edit, a typing indicator — which cancels the pending decision and starts the wait over), and a message that commits while it waited **supersedes** it: its own turn (queued behind this one) decides over the still conversation, so a burst of messages settles into one decision (the newest turn's) over what was actually said, the older decisions cancelled (no call, no typing indicator, nothing recorded). The decision is one small call over the channel transcript (`bot/chime.ts`; the transcript is cut at the triggering message — the newest user message, though a previous turn's reply can sit after it in the context — and the reply's system prompt is not part of it; tool results, the rounds' tool calls and reasoning are stripped from it — the decision is about the conversation, not a past turn's tooling) reported as a call of the `chime` tool with a `respond` flag and a required `reason` (endpoints that ignore the tool fall back to a plain leading-word YES/NO answer, the rest of it as reason). YES runs a normal turn (streamed reply, tools and all); NO posts the decision + reason to the channel as a one-line UI message (🔕, reason truncated, never tracked); a garbage/empty answer or a failed call stays completely silent (no typing indicator, no message, nothing recorded — a broken decision must not post an unasked-for reply). An activity during the in-flight decision call aborts it (`InterruptedError`, re-thrown): the turn waits for stillness again and starts a new decision over the updated transcript. Mentions from any author always respond (no decision, no stillness wait).
- **Clear** — `!clear` in a text channel resets that channel's model context for a fresh chat: `reset()` drops entries + summary, sets the clear's *watermark* (time) and suppresses the startup seed (no re-seed; a clear committed while the seed fetch is still in flight wins — the late fetch is discarded). The clear **survives a restart**: the reset context (and the watermark) is persisted, an empty context never re-seeds, and the restart catch-up seed never re-imports messages older than the watermark (a restart does not resurrect the cleared conversation). The command is neither tracked nor answered (a bot mention alongside it is swallowed too); only humans may issue it (other bots' messages are tracked now, so a bot posting `!clear` is just context). The bot posts a confirmation line (🧹, a UI line, never context). Mentions queued before the clear are skipped (their message left the context).
- **Turn** — `runToolTurn` (`tools/loop.ts`): model ↔ tool rounds capped by `TOOLS_MAX_ROUNDS`. When the turn ends, the **whole turn is recorded** in the channel context (`appendTurn`): each executed round (the model's text, its reasoning, the calls it requested, the results in order — the round's text is recorded with the message ids its narration settled to, so edits/deletes of those messages keep syncing) and the final reply (canonical posted text, chunk ids). The model's reasoning is also sent back to the endpoint as `reasoning_content` on the assistant messages (within the turn, so a reasoning model continues from its own thinking; and across turns/restarts via the persisted entries — endpoints without reasoning support ignore the field). The turn's activity message (one per turn — the thinking (🤔) terminal lines and the tool-call lines interleaved in the order they happened; posted on the first line, edited in place for every later line, oldest lines collapsing into a "… N earlier activity lines …" header past 2000 chars) is posted for humans only — never context.
- **Images** — `MODEL_ENABLE_IMAGES=true`: image attachments (png/jpeg/webp/gif) of the newest `MODEL_CONTEXT_MAX_MESSAGES` entries are downloaded per turn from the Discord CDN (≤4 per message, `MODEL_IMAGES_MAX_BYTES` cap) and sent as base64 `image_url` parts; unsent attachments leave a one-line note.
- **Files** — `MODEL_ENABLE_FILE_CONTENTS=true`: the text content of non-image attachments of the newest `MODEL_CONTEXT_MAX_MESSAGES` entries is downloaded per turn from the Discord CDN (≤3 per message, `MODEL_FILE_CONTENT_MAX_BYTES` cap) and inlined into the message's context text as a labeled, fenced block (the fence grows past any backtick run in the content). Only readable text (valid UTF-8, no NUL bytes) is inlined; binary files, oversized ones, and download failures leave a one-line note. The pipelines are mutually exclusive per attachment type: with file contents on, the image pipeline only references image attachments (no "unsupported type" notes for files); off, behavior is unchanged.
- **Tools** — four opt-in in-process families (default `false`): `WEBTOOLS_ENABLED` (DuckDuckGo search + SSRF-protected fetch), `FILETOOLS_ENABLED` (read/write/edit confined to `FILETOOLS_WORKSPACE`, default `./workspace`, which must exist), `SHELLTOOLS_ENABLED` (run a shell command via /bin/sh in the file workspace; per-command deadline + combined output cap), `ZIMTOOLS_ENABLED` (offline Wikipedia, `ZIM_FILE` → ZIM v6 archive). The system prompt note (`tools/index.ts`, built by `buildTools`) lists exactly the enabled families — the model is never told about disabled ones; the ZIM no-match hint only suggests `web_search` when the web family is enabled.
- **Metrics** (`llm/metrics.ts`) — the model side's own tokenizer counts. `LlmClient.chat` captures `ChatResult.usage` whenever the response reports token counts (OpenAI `usage` block; llama.cpp's legacy top-level `prompt_tokens`/`completion_tokens`; or the `timings` block the final streaming chunk carries — `prompt_n + cache_n` prompt tokens, `predicted_n` completion tokens; llama-server sends the first two non-stream and timings stream). Every model call of a turn (reply tool rounds, the compaction summarizer, the chime decision) runs through a `TurnTokens` wrapper: at the end of the turn the summed input/output tokens are logged, and the turn's largest prompt becomes the channel's *measured* context size — what the compaction trigger compares against `CONTEXT_COMPACTION_MAX_TOKENS` in preference to the char estimate (a compaction attempt forgets it; `!clear` does too). With `MODEL_METRICS_ENABLED` the llama-server's `GET /slots` (base `MODEL_METRICS_URL`, default the chat endpoint's origin; per-probe timeout `MODEL_METRICS_TIMEOUT_MS`) is additionally probed at startup and after every turn: the context window and current use are logged ("server context X/Y tokens"), the startup probe warns when the compaction budget is not below the window, and when the endpoint reports no usage the slot's last-request token count is the fallback measurement. With `CONTEXT_COMPACTION_MAX_TOKENS` left empty (present but blank; a missing variable keeps the default), the budget is set automatically from the first successful probe: window minus the completion headroom (4096 tokens, `COMPACT_OUTPUT_RESERVE_TOKENS`) — the 4000 fallback applies until then, and a too-small window gives up after one warning. All probes are best-effort — a broken endpoint resolves to null and never kills a turn.
- **Overflow recovery** (`index.ts`) — when a turn's request overfills the model's context, the endpoint rejects it before generating (llama.cpp: HTTP 400, `"request (N tokens) exceeds the available context size (M tokens)"` — JSON body in stream and non-stream alike). The bot recognizes the overflow error (`isContextOverflowError`, a few endpoint phrasings), reads the window from the error when it carries one, shrinks the channel context with `emergencyShrink` (oldest entries first, never the turn's mention; the running summary is dropped only when the entries alone still do not fit; target = the smaller of the compaction budget and window − headroom), rebuilds the turn's context, and retries the model once — a second overflow (e.g. the mention alone is too big) falls through to the ordinary error path. The pre-overflow measurement is forgotten (it described the overfilled context).

## 2. Build & Development Commands

```bash
npm install               # npm only (package-lock.json present)
cp .env.example .env      # fill in values; .env is gitignored
npm run dev               # run from source (tsx)
npm run build && npm start  # compile src/ -> dist/ and run
npm run typecheck         # tsc --noEmit
npm test                  # smoke tests (tsx test/smoke.ts)
```

- **Done means green**: `npm test` **and** `npm run typecheck` — `tsx` does not typecheck, so a green test run proves nothing about types.
- Required env: `DISCORD_TOKEN`, `MODEL_API_URL`; `DISCORD_GUILD_ID` is optional (empty = respond in every text channel of every guild the bot is in); everything else in `.env.example`.

## 3. Testing Guidelines

- Whole suite is `test/smoke.ts` via `npm test` — no framework, no selection, no config. Hermetic: mock OpenAI-compatible HTTP server on an ephemeral port, fake Discord channels, injected DNS/search backends, temp workspace dirs; no `.env`/Discord/network needed.
- Plain `node:assert/strict`; `ok(name)` check groups (currently **156**); the final line prints the count.
- Async is driven with `ticks()` (`setImmediate`), not real sleeps.
- In tests use the pure `parseConfig(env)`, never `loadConfig()` (calls `process.exit(1)`).
- Web-tool tests use `WebToolsOptions.allowPrivate`/`resolver`/`searchFetch` — tests-only escape hatches, never enable in production.

## 4. Code Style & Naming Conventions

- Relative imports need explicit `.js` extensions even in `.ts` files: `import { x } from "./bot/queue.js"`.
- 2-space indent, double quotes, semicolons; `import type` for type-only imports; explicit return types on exported functions; JSDoc on exported symbols.
- Lowercase error messages without a trailing period; log via `src/log.ts`, never bare `console.log` outside `log.ts`/config errors.
- Defensive by default: malformed model input/SSE/Discord errors are tolerated where it keeps the bot alive; a broken tool becomes an `Error: …` tool result, never a crash.
- Naming: `PascalCase` types, `camelCase` functions/vars, `UPPER_SNAKE` constants/env, lowercase filenames.
- Do not add runtime dependencies without confirming with the user.

## 5. Working Agreements

- The user drives commits — don't commit unless explicitly asked (style: conventional subjects, `feat: …`/`fix: …`).
- Never edit or commit: `dist/`, `workspace/`, `.env`, `node_modules/`.
- Ask before: changing queue/history/writer/context semantics pinned by tests, changing the SSRF blocklist or workspace-confinement rules, or enabling tools in `.env`.
- No CI — `npm test` + `npm run typecheck` are the only gates; keep changes self-contained.

## Behavior pinned by `test/smoke.ts` (change only together with the tests)

- **Queue**: per-channel FIFO; one turn at a time per channel (channels run concurrently); holds *turn requests* `{id, chime}` in arrival order — mentions (`chime: false`, always respond) and, with `BOT_CHIME_ENABLED`, any other non-mention message (`chime: true`); a trigger whose message left the context is skipped. `newestPendingMentionAfter(id)` reports the newest pending mention turn whose trigger is newer than `id` (snowflake order), null when none — the interrupted-turn supersede check (see Prompt interruption) asks the queue which newer mention will answer the channel.
- **Chime**: `decideChime` is one chat call (system prompt + transcript) with the `chime` tool on the wire — the decision is the model's call of it (`respond` boolean, a `"yes"`/`"no"` string tolerated, plus a `reason`; a missing reason is "", a missing/unusable `respond` is a broken decision). An endpoint that answers in plain text instead falls back to the leading-word parse (YES/NO, the rest of the answer is the reason); garbage, an empty answer, and a failed call all stay silent (logged, nothing posted). A NO posts `🔕 *chime: no — <reason>*` (reason trimmed, newlines collapsed, truncated to 200 chars) as a UI line — never context. A chime turn decides over a still conversation: it waits for complete stillness in the channel (`waitForQuiet`, `DISCORD_MESSAGE_STABLE_MS` — any activity while waiting restarts the window and cancels the pending decision) **before** building the context and deciding, and `context.newestUserEntryAfter(trigger)` cancels the decision when a newer user entry (a trackable message that committed while it waited or while the context was built) supersedes it — the newer message's own turn (queued behind) decides over the still conversation, so a burst of messages settles into one decision (the newest turn's); assistant and tool entries never supersede (they are the bot's own words). The decision itself runs after the context is built (seed + compaction included) and before the writer starts, so a NO leaves no typing indicator and no reply; a cancelled/superseded chime records nothing (no call, no typing indicator, no message). An *interrupted* decision call (`InterruptedError` — the channel changed while the decision was in flight, or activity aborted the not-yet-started attempt while it waited for stillness) is re-thrown, not swallowed into a silent NO: the turn waits for the channel to go quiet, then discards the decision when a newer message supersedes it (the newer message's own turn decides over the still conversation) or retries it (a fresh attempt: stillness wait, fresh context, supersede check, new decision — an interrupted decision is not lost). `newestUserEntryAfter` reports the newest user entry after the trigger's entry (entries sit in commit order), null when the trigger is gone or nothing newer follows.
- **Stability gate**: a message commits exactly once, when it has been unchanged for `DISCORD_MESSAGE_STABLE_MS` (edits restart the window; the commit carries the latest state); a stale timer re-firing is a no-op (only the still-stored entry commits). A message dropped while pending (delete / channel delete / shutdown) never commits, even if its cancelled timer fires. `onCommit` (in `index.ts`) evaluates the *final* content: a human's `!clear` resets the context and is neither tracked nor answered; otherwise the message enters the context (labeled `(bot)` for bot authors) and a mention from any author queues exactly one turn — an edit that adds or removes the mention before stabilization decides. Edits after the commit sync the context in place (a chunked reply is one entry with one id per chunk; any chunk id resolves it; a chunk edit rebuilds the text; a chunk delete drops the whole reply). The chunked-reply chunks store the RAW posted text, so the bot's own final settle edit (which Discord echoes back as a messageUpdate) is a no-op against them and only a real edit — by anyone — changes anything; a single-message entry instead takes the mention-stripped content, and its stored attachment metadata follows the edit (the image/file pipelines download from it at turn time); deletes remove the entry.
- **Prompt interruption** (`bot/quiet.ts`): `ChannelActivity` records per-channel changes (`note` — a new trackable message, an edit, a typing indicator; the bot's own never) and resolves `waitForQuiet(channelId, quietMs)` once the channel has been unchanged for `quietMs` after its newest change — every new change while waiting restarts the window from that change; a channel with no recorded activity (or a cleared one) is quiet at once. `watch(channelId, onActivity)` fires the callback on every note (a running attempt uses it to abort its in-flight request) and returns an unsubscribe; `clearChannel`/`clear` forget state + watchers (a deleted channel's turn must not keep waiting). In `index.ts` the turn runs in attempts: while an attempt is running, any note for its channel aborts its model request (`LlmClient.chat`'s `signal` → `InterruptedError`, never a timeout); the attempt's partial reply is withdrawn (`writer.interrupt()`), the turn waits for the channel to go quiet (`DISCORD_MESSAGE_STABLE_MS`), and the interrupted turn is judged — **superseded → discarded** (never completed later, nothing recorded, so the model responds to the newest information through the newer turn: a chime turn is superseded by any newer committed user entry via `context.newestUserEntryAfter(trigger)`, a mention turn by a newer pending mention turn via `ChannelQueue.newestPendingMentionAfter(trigger)`, double-checked against the context so a deleted trigger supersedes nothing; a newer *ambient* message does not supersede a mention turn — chime off queued it no turn, chime on its decision may stay silent — the mention must still be answered) and **not superseded → retried** (the interruption carried no new message — an edit, a typing indicator — so the fresh attempt's context carries everything that arrived or changed while it waited). An interrupted attempt records nothing in the channel context either way (only the attempt that completes is recorded); a turn whose trigger left the context while it waited for quiet skips.
- **Clear**: `!clear` (trimmed, case-insensitive, bot mentions stripped, evaluated on the committed/final content) resets the channel context: `reset()` drops entries + summary, marks the seed as taken (no re-seed) and stamps the clear's watermark — a pre-clear mention → null. The reset (and the watermark) is persisted: an empty context never re-seeds after a restart, and the restart catch-up seed never re-imports messages older than the watermark (the clear survives a restart). The 🧹 confirmation line is a UI line, never context; the command itself is never tracked or answered. Only human authors may issue it (other bots' `!clear` is just a tracked message).
- **Compaction**: the seed (a channel without a persisted context, or the one restart catch-up of a restored conversation) merges the live last-N with what already arrived, chronologically by `createdTimestamp`, ties broken by snowflake id (`compareDiscordIds` — the API returns newest-first, so same-millisecond bursts must not keep that order; tracked ids win), honoring the clear's watermark (no message older than the latest `!clear` is imported). The seed fetch is capped at Discord's 100-message limit (a bigger window seeds with what Discord can give). The bot's own UI lines — the turn's activity message (one per turn, edited in place: the thinking terminal lines and the tool-call lines interleaved in the order they happened, so its first line is "🤔 *…*", "🔎 *…*", "📁 *…*", "🐚 *…*", "📚 *…*" or "🔧 *…*", or the "🔧 *… N earlier activity lines …*" header once the oldest lines are dropped), the clear confirmation (🧹) and the chime NO line (🔕) — never enter the model context, and the seed must not re-introduce them after a restart (the tool-round narrations ARE tracked — as the round entries of the turn's record — so they enter the context live, not via the seed). The trigger size is the channel's measured tokens (the endpoint's own count of the last turn's largest prompt) when known, else the char estimate (reasoning and tool calls counted) — over budget → `compact()` folds everything older than the keep window (plus any existing summary) via one tool-less call — never the turn's mention — and the fold boundary never splits a tool-call group (a group straddling it folds whole into the summary); the measurement is forgotten (it then describes the pre-compaction context); on summarizer failure or nothing foldable → `emergencyTrim` drops the oldest entries (never the mention) whole-group until the estimate fits. An empty (present-but-blank) `CONTEXT_COMPACTION_MAX_TOKENS` switches the budget to automatic: window minus `COMPACT_OUTPUT_RESERVE_TOKENS` headroom from the first successful /slots probe (4000 fallback until then; too-small window → give up after one warning; missing variable = the plain default). If a request overfills the window anyway, `isContextOverflowError` (llama.cpp's `exceed_context_size` rejection, a few other phrasings) → `emergencyShrink` (oldest first, mention never dropped, summary dropped last) to `min(budget, window − headroom)` → rebuild → **one retry** (the rounds the failed attempt already ran are dropped from the turn's record — the retry starts from the rebuilt context, so they are not part of the conversation the model completed); a second overflow is the ordinary error path.
- **Turn context**: system prompt first, then the summary as a labeled user message, then entries in order — user entries prefixed `Name: …` (`Name (bot): …` for other bots), assistant entries (the bot's replies, and each tool round's narration) as unlabeled messages carrying their `toolCalls` and `reasoningContent` (a round that answered with calls only renders on its calls), tool results as `tool`-role messages paired by `toolCallId`, textless entries with no images, no file blocks and no tool calls dropped. If the mention is no longer in the context (deleted), the turn is skipped. The reply request always ends with the trigger's user message (`endWithTrigger`): a message committed while the previous turn is still in flight lands in the context *before* that reply (the reply is recorded when the turn ends), so the context can end with the bot's own reply — a request in that shape makes a prefill-assistant endpoint (llama-server's `prefill-assistant` default) continue the trailing assistant message, echoing it back verbatim as the new reply (the duplicate post) or rejecting the request when two replies trail ("Cannot have 2 or more assistant messages at the end of the list"); the trigger is moved to the end of the rendered array (the rest keeps its order; a no-op when it is already last), and the chime decision's transcript is unaffected (still cut at the trigger's original position). Every message is its own user message, never merged; recorded replies appear once with canonical text; deleting a round's narration message drops the whole call/result group (never calls without results, never orphaned results); the 🤔/🔎 activity lines never appear (the full reasoning is in the context as `reasoningContent`, the activity lines are UI).
- **LLM client**: the per-request timeout covers the whole stream; `abort()` cancels all in-flight requests (reported as a timeout). `chat()` takes an optional caller `AbortSignal`: a pre-aborted signal fails the request at once with `InterruptedError` (no request goes out), and aborting it mid-flight cancels the request immediately (fetch/stream aborted at once, not at the timeout) — both reported as `InterruptedError`, never a timeout (the channel-activity interruption; the turn catches it, waits for quiet, and either discards the turn when a newer turn supersedes it or retries it). `tools`/`tool_choice` are sent only with a non-empty registry; streamed `delta.tool_calls` are reassembled by index. `chat()` takes `StreamCallbacks { onDelta?, onReasoning? }`; the reasoning (`reasoning`/`reasoning_content` deltas, streamed or non-stream) is handed to `onReasoning` **and** accumulated on `ChatResult.reasoning` (so the caller can record it and send it back). An assistant message's `reasoningContent` is emitted on the wire as `reasoning_content` (plain and with `tool_calls` alike; no field when absent). `ChatResult.usage` is set whenever the response reports token counts — `usage` block, llama.cpp's legacy top-level counters, or the final chunk's `timings` (prompt_n + cache_n / predicted_n) — and left absent otherwise. Message `content` is a string or an array of text/image parts (pass through to the wire unchanged); `tool` messages serialize to `{role: "tool", tool_call_id, name, content}`.
- **Writer**: ≤2000 chars; `splitForDiscord` never splits inside a code fence (closes it, reopens in the next chunk), keeps tables together (a spanning table repeats its header row), prefers paragraph/heading/list boundaries. The turn's **activity message**: ONE message per turn (posted on the first line, edited in place for every later line — the channel stays quiet no matter how many rounds run) holding the UI lines **in the order they happened**: each round's thinking terminal line, then the tool-call lines the round requested. While a round is thinking, its live preview shows at the bottom of the message (whole text while it fits the remaining room; otherwise header + "*N lines hidden*" + last 5 lines, budgeted so the whole message stays ≤2000); the preview completes in place to the terminal line — the first line of the thinking (truncated after 50 chars, `...` when cut) plus how long it took, e.g. "🤔 *Let me check the units first. (12s)*" — when the reply starts, when a tool round ends (`discard()`), or at finish when nothing streamed; every round's reasoning thus persists as its own terminal line in the one shared message, not just the final one's (a `*` from the model's text is dropped from the displayed thinking — the line is wrapped in italics and a markdown bullet or bold would break the wrapping; the tool-activity lines do the same). Past 2000 chars the oldest lines are dropped behind a "🔧 *… N earlier activity lines …*" header that keeps a leading icon so the message stays a UI line (never context); a failed post is retried by the next line (the retry carries every line so far), a failed edit keeps the last good content. The reply then streams in its own fresh live message(s) (only the growing last chunk is edited, throttled; a new live message is created per chunk; each settles in place at finish, remaining chunks posted fresh). The channel shows a one-line summary of the reasoning, never the full text (the full reasoning lives in the model context, not in the channel). `discard()` (used between tool rounds, **awaited** by the tool loop) settles the round's reply text in place (the live messages are completed to the round's full text, so the round's narration stays in the channel above the next activity lines) and appends the round's terminal line to the shared message (the next round's preview and lines continue in it); it **resolves with the settled round** (`PostedReply` — message ids + text, `null` for a textless round) so the caller can record it in the channel history. `interrupt()` (a prompt interrupted by channel activity) stops the typing indicator, completes the round's thinking line in the shared message (kept, like a finished round's), and deletes the reply's live partial messages — the caller then waits for quiet and either discards the turn (a newer turn supersedes it) or retries it with a fresh writer, so the partial text never lingers as a broken reply either way; a no-op when the writer never started or already finished (nothing posts after it). `format.ts` rewrites `$…$` math to Unicode before posting/record (non-math `$` untouched).
- **Tool loop**: a round ending in tool calls is reported to the caller in full — `onToolRound` (**awaited** first: it settles the round's streamed text in place via `writer.discard()`, so the narration stays above the next activity lines, and the caller captures the settled ids), then `onToolCalls` (the caller records the calls in the turn's shared activity message via `writer.appendActivityLines` — the turn's first line posts the message, every later line (thinking terminal lines and call lines alike) edits it in place in the order they happened, so a turn with N calls across R rounds costs one new Discord message, no matter how many rounds run; past 2000 chars the oldest lines are dropped behind a "🔧 *… N earlier activity lines …*" header that keeps a leading icon so the message stays a UI line; a failed post/edit is retried on the next line. Each line: icon + name + up to two args (`formatToolCall`), results never shown), then the tools execute concurrently, and `onRoundComplete` fires with the `ToolRound` (the round's text + reasoning + calls + results) — the caller records the turn in the channel history, so the model's history keeps every round (the next request carries the round's assistant message with its `reasoningContent` + `toolCalls`, then the tool results). `onToolRound`/`onRoundComplete` never fire for the cutoff round — its text is the final reply, posted (and recorded) by the caller's `finish()`, and its unexecuted calls are not recorded (a history carrying them would be invalid). `TOOLS_MAX_ROUNDS` caps the rounds; exhaustion with no text posts a note.
- **Persistence**: one JSON file (`CHATS_FILE`, default `./data/chats.json`, gitignored) holds every channel's context — entries (the full turn conversation: text, reasoning, tool calls, results, chunks, ids), the summary, the seeded flag, the clear's watermark, the measured size. Every context change saves (coalesced: at most one disk write per tick; atomic: temp file + rename); a missing file (first run) or a corrupt file (crash mid-write) fails soft to an empty store — the old re-seed behavior. `!clear` persists (an empty context never re-seeds; the watermark keeps the restart catch-up from resurrecting the cleared conversation); a deleted channel is removed from the file; shutdown flushes the pending write before exit. Restore validates entry-by-entry (a malformed entry is skipped, not fatal).
- **Tool security**: `web_fetch` validates URLs against an SSRF blocklist, connects to the pinned resolved IP (anti-DNS-rebinding), re-validates redirects hop by hop, and refuses mixed public/private resolution. File paths are confined to the workspace (symlink escapes, including dangling, rejected); reads refuse binaries, writes are capped. `shell_exec` is not sandboxed — commands run via /bin/sh in the file workspace with a per-command deadline and a combined output cap (a kill returns the partial output); in-flight commands are killed with the tool stack. ZIM reads are read-only and bounded: single fd with targeted reads (never mmap'd), size-capped LRU entry/cluster caches, time-budgeted title scans, hop-capped redirects with loop detection.

## Gotchas

- The bot needs the **MESSAGE CONTENT privileged intent** enabled (Developer Portal → app → Bot → Privileged Gateway Intents); without it, message content silently arrives empty.
- `MODEL_ENABLE_IMAGES=true` requires a vision-capable endpoint; images are downloaded at turn time only (last-N window), never on message arrival. File contents (`MODEL_ENABLE_FILE_CONTENTS`) are likewise inlined at turn time only; a non-text file (binary, NUL bytes, invalid UTF-8, empty) is never inlined — it leaves a note, like an oversized image.
- Keep `CONTEXT_COMPACTION_MAX_TOKENS` comfortably below the llama-server context size (`-c`, default only 4096), and `CONTEXT_COMPACTION_KEEP_MESSAGES` small enough that keep-messages + summary fit — otherwise `emergencyTrim` starts dropping recent messages. Without metrics the trigger is a char heuristic (~4 chars/token), not a real tokenizer; with `MODEL_METRICS_ENABLED` (or any endpoint that reports usage) it is the endpoint's measured prompt count instead — note it includes the chat-template overhead, so it runs slightly higher than the estimate for the same content. The automatic budget (empty `CONTEXT_COMPACTION_MAX_TOKENS`) derives window − 4096 — that keeps the window nearly full, so prompts (and prompt processing) get large; pin a smaller number when per-request latency matters. Overflow recovery (one shrink + retry) catches what slips past the budget, but it drops the oldest messages without a summary — the budget should still do its job. With metrics on, the startup probe warns when the budget is not below the server's context window. Note the context now grows by a *whole turn* per turn (every round's text, reasoning, calls and results are recorded, not just the final reply), so with tools enabled the budget fills faster than before — a chatty tool run can add several thousand tokens.
- The `CHATS_FILE` (`./data/chats.json`) is the source of truth for the conversation after the first turn in a channel: a restart resumes from it (no re-seed), and a channel whose context was `!clear`ed stays cleared. Back it up if the conversation history matters — deleting the file makes the bot re-seed the channels' last-N text (losing the reasoning and tool history). A corrupt file (crash mid-write) degrades to the same re-seed behavior and logs a warning.
- The endpoint must support function calling (llama.cpp needs a tool-capable chat template); if it rejects `tools`, keep the `*_ENABLED` flags off. Note `BOT_CHIME_ENABLED` also sends one tool on the wire (the chime decision) — the decision call fails soft (the turn stays silent), but a `tools`-rejecting endpoint will never chime.
- `FILETOOLS_WORKSPACE` (default `./workspace`) must exist — not created automatically; failures surface per call and the turn continues. The shell tool runs in that same directory, so it needs the directory too.
- ZIM: v6 only (Wikipedia clusters are zstd-compressed → Node >= 22.15); LZMA2 clusters/non-v6 surface as per-call errors, never crashes. `wikipedia_search` matches titles/paths only (exact → prefix → budgeted substring scan), not article bodies; `wikipedia_read` returns clean text (references/TOC/nav dropped), truncated to `TOOLS_MAX_RESULT_CHARS`.
